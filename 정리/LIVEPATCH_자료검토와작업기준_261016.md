# LIVEPATCH 자료 검토와 작업 기준

> 이 문서는 수정 전 초기 검토 기록입니다. 발견 항목의 현재 처리 결과는 `LIVEPATCH_v5.7_변경검수결과_261016.md`, 출시 범위와 Figma 순서는 `LIVEPATCH_MVP범위와Figma작업순서_261016.md`를 따릅니다.

검토일: 2026-10-16. 대상: LIVEPATCH 폴더의 기획·명세 9개 파일과 PNG 221개. 현재 자료는 제품 설계 및 목업 단계다. 배포 가능한 애플리케이션 소스, 빌드 설정, 실행 테스트 결과는 이 폴더에서 확인되지 않았다.

## 1. 제품 이해

LIVEPATCH는 기존 웹사이트를 운영하는 비개발자가 화면의 요소를 선택하고 말이나 터치로 변경을 요청하는 웹 서비스다. 변경안을 미리 보고 검증·승인한 뒤 운영 사이트에 반영하며, 문제 발생 시 복원을 요청한다. 설치형 데스크톱 앱·브라우저 확장·모바일 설치앱은 최초 출시 범위에서 제외한다. 사이트 연결에 필요한 OAuth·플러그인·스크립트 설정과 사용자용 프로그램 설치는 구분한다.

공식 웹사이트는 이해·체험·가입·가격·결제를, 고객 콘솔은 사이트 연결·편집·승인·작업 및 구독 관리를, 관리자 콘솔은 지원·결제·권한·장애·감사를 담당한다. 제품의 핵심 설계 대상은 고객 콘솔의 Visual Patch Studio다.

최신 방향은 **선택 → 음성 요청 → 의도 확인 → 미리보기 → 승인·반영 → 결과 확인·복원**이다. 고객의 키보드 사용과 운영팀의 수동 개입을 줄이는 것이 목표다. 무개입 해결률 90% 이상은 문서의 목표이며 달성 실적이 아니다.

AX는 우선 AI가 사용자 의도를 해석하고 불확실성을 확인하며 실행 결과를 설명하는 경험으로 다룬다. 접근성도 별도 품질 기준으로 함께 검토한다.

## 4. UX UI AX 검토

### 유지할 설계

- 고객 사이트가 중심이 되는 모노크롬 레이어와 선택·주요 행동에 제한한 파란색 사용.
- 번호 선택, 음성 입력, 의도 확인 카드, 실제 사이트 위 미리보기의 연결.
- 미리보기와 운영 반영 분리, 원본 매핑 불확실 시 중단, 승인 후 원본 변경 시 재검증.
- 원본 수정·CMS 데이터 수정·표시 패치의 차이를 계속 보여 주는 방식.
- 실제 서버 결과에 따른 배포 상태, Trace ID를 이용한 지원, 크레딧 예상·보류·확정의 구분.
- 관리자 UI 재사용과 별개로 운영 흐름·권한·위험 조작을 검수하는 원칙.

### 다음 디자인에서 보완할 점

- 음성 시작, 녹음 중, 인식 결과, 의도 확인, 미리보기 생성은 서로 다른 행동이다. 버튼 이름과 실제 이벤트를 일치시킨다.
- 숫자·금액·날짜·전화번호는 인식 원문과 정규화된 값을 확인 카드에서 구분한다. 불확실한 부분만 후보 선택으로 확인한다.
- 마이크 권한 거부·소음·인식 실패·네트워크 중단 때 제안 칩·터치·텍스트 대안으로 작업을 이어간다.
- 길게 누르기는 승인 의사를 표현하는 조작이다. 권한·재인증·변경 해시·검증 통과를 대체하지 않는다. 키보드·보조기기 대안에서도 같은 승인 절차를 적용한다.
- AI 제안은 근거·적용 범위·비용을 보여 주며 수락 전 운영 반영을 하지 않는다.
- 기본 목업을 로딩·빈 상태·권한 없음·오류·오프라인·배포 결과 불명·복원 실패 상태로 확장한다.
- 대표 목업 12개를 시각 검토했다. 구조와 색 사용 방향은 일관되나, 실제 콘텐츠의 정보 밀도·작은 텍스트·터치 영역·장문·실패 상태는 Figma 및 실행 환경에서 추가 확인한다. 전체 221개 이미지의 세부 시각 검수를 완료한 것은 아니다.

## 6. 디자인부터 배포까지 작업 순서 제안

1. **제품 계약 정리:** R02~R04·R07·R08의 정책과 첫 커넥터 범위 확정. 가격·법무·음성 공급사·보존 기간은 결정 레지스터에 유지.
2. **핵심 여정 설계:** 데모 M01/M02 → 가입 M24~M26 → 연결 C02~C09 → 편집 C13 및 O34~O40 → 작업·배포·복원 C14/C15/C18/C19. 조건과 실패 분기를 함께 설계한다.
3. **Figma 기반 구성:** 공통 토큰·컴포넌트·상태를 만들고 핵심 여정부터 프레임과 프로토타입을 제작한다. 기존 ID로 명세를 연결한다.
4. **운영·과금 연동:** 실제 출시 기능에 필요한 고객 과금·지원, 관리자 문의·배포·원장·감사 화면을 함께 연결한다. 나머지 화면은 범위 확정 후 순차 제작한다.
5. **Codex 구현 및 검증:** 실행 가능한 저장소를 준비하고 OpenAPI·타입·권한·이벤트를 연결한다. 승인 우회·중복 요청·동시 변경·배포 결과 불명·복원 실패를 포함한 E2E를 수행한다.
6. **제한 파일럿 후 배포:** 테스트 사이트에서 실제 원본 변경과 복원을 검증하고, 호환성·작업 시간·비용·개입률을 측정해 가격·지원 범위를 조정한다.

위 순서는 신규 작업 제안이며, 기존 릴리스 분류를 임의 변경한 것이 아니다. 일정과 완료율은 아직 산정하지 않는다.

## 7. 앞으로 지킬 제작 기준

- Figma 레이어 이름에 `/`를 넣지 않는다. Auto Layout을 기본으로 하고 실제 캔버스 좌표·선택 경계 등 필요한 경우만 absolute 배치한다.
- 프레임은 1440/1024/768/390 기준, 추가 검수는 360·1920. 관리자 모바일은 조회·긴급 확인 범위를 별도 정의한다.
- 최상위 CTA는 현재 단계의 행동 하나로 명확하게 만든다. 목업의 샘플 값·테스트 통과 표시는 실측 데이터로 오인되지 않도록 분리한다.
- AI가 이해한 내용과 실행한 내용을 구분하고, 성공은 서버 결과 확인 후 표시한다. 실패 문구에서 실제 데이터 영향 여부를 근거 없이 단정하지 않는다.
- 산출물 파일명 끝에 `_YYMMDD`를 붙인다. 원본 자료는 보존하고 후속 변경은 변경 이유와 함께 기록한다.
- 디자인 완료·개발 준비 완료·배포 완료를 서로 다른 상태로 관리한다.

# LIVEPATCH 디자인킷 분석

분석일 2026-10-16. 추가된 `AGENTS.md`, `docs/design.md`, `docs/style.md`와 연결된 `src/styles/design-tokens.css`를 검토했다. 이번 작업은 분석이며 원본 문서·CSS·Figma는 수정하지 않았다.

## 1. 구성과 준비 수준

| 파일 | 역할 | 현재 상태 |
|---|---|---|
| AGENTS.md | 작업 분류·문서 우선순위·Figma·검수 실행 규칙 | 즉시 적용 가능한 제작 규칙 |
| docs/design.md | 프로젝트 목적·콘셉트·콘텐츠·페이지·토큰·검수 브리프 | LIVEPATCH 정보가 들어 있지 않은 양식 |
| docs/style.md | 한국어 중심 시각 취향과 금지 패턴 | 반복 사용 가능한 스타일 기준, 승인 패턴은 아직 없음 |
| src/styles/design-tokens.css | 서체·색·간격·컨테이너·형태·상태·레이어·기본 CSS | 구현용 기초 토큰. LIVEPATCH 역할별 조정 필요 |

기초 토큰까지 갖춘 디자인 제작 프레임워크다. 완성된 Figma 컴포넌트·Variant·프로토타입이 포함된 UI 킷으로 보기는 어렵다. 기존 화면 계약을 이 기준으로 표현할 수 있지만, 브리프 작성과 제품별 토큰 연결이 먼저 필요하다.

## 2. 기존 방향과 잘 맞는 부분

- 화이트·뉴트럴 중심, 브랜드 색 절제, 한국어 타이포그래피 우선은 LIVEPATCH의 모노크롬 편집 레이어와 일치한다.
- 실제 제품 UI와 실제 한국어 콘텐츠를 사용하고 추상 AI 장식·임의 통계를 배제하는 기준은 서비스의 수정·확인·반영 경험을 설명하는 데 적합하다.
- 카드보다 구획·선·여백을 먼저 검토하는 방식은 공식 웹의 정보 위계와 관리자 테이블에 모두 활용할 수 있다.
- 편집 가능한 Figma 레이어, Auto Layout, Component/Variant, Variables/Styles, `/` 없는 이름 규칙은 기존 제작 원칙과 일치한다.
- 상태·오류·접근성·실제 콘텐츠 검수, 자체 검수와 사용자 승인의 분리는 유지할 기준이다.
- 폰트 본문 1rem, 보조 0.8125rem, 4px 기반·8px 우선 간격, 역할별 radius는 공통 Foundations의 출발점으로 쓸 수 있다. 픽셀 환산은 루트 폰트 16px을 가정한다.

## 3. 충돌과 적용 경계

| 항목 | 확인 내용 | LIVEPATCH 적용 방향 |
|---|---|---|
| Figma 기본 폭 | 새 킷은 PC 1920px·콘텐츠 1440px, 기존 계획은 대표 1440px | 앞으로 메인 시안은 새 킷의 1920/1440을 기본으로 사용. 이전 1440px은 구현 검수·기존 목업 기준과 구분 |
| 모바일·태블릿 시안 | 새 킷은 별도 요청 때만 생성, 이전 계획은 여러 폭의 프레임을 전제로 함 | 우선 PC 시안 제작. 모바일·태블릿 Figma 프레임은 자동 추가하지 않음. 제품의 모바일 조회 기능·웹 반응형 요구는 유지 |
| 공식 웹과 Studio 레이아웃 | 킷은 Hero·섹션·중앙 컨테이너 중심 | 공식 웹에 우선 적용. Studio는 고객 사이트 캔버스가 중심인 전체 가용폭 작업 공간으로 구분하고 중앙 1440px 제한을 일괄 적용하지 않음 |
| 프로젝트 브리프 | 서비스명·사용자·핵심 행동이 모두 미확정으로 남아 있음 | 기존 대화와 v5.7에서 이미 확인한 내용을 채울 대상. 제품 정의를 다시 질문하거나 미확정으로 되돌릴 이유 없음 |
| Primary 의미 | CSS Primary는 검정 #17191D, Accent는 파랑 #2764E7. 기존 주요 행동·선택은 #2563EB | 검정을 시각 베이스, 파랑을 제품 주요 행동/선택으로 역할 매핑. 색상 이름만 보고 기본 버튼을 검정으로 고정하지 않음. 파랑 HEX는 한 값으로 통일할 필요 |
| 성공·주의 색 | CSS에 초록·주황 Semantic 토큰 존재 | 라이브러리에 존재하는 것과 Studio에 노출하는 것을 구분. Studio는 중립색+아이콘+문구, 위험은 빨강. 모든 배지에 색을 추가하지 않음 |
| 헤더 높이 | CSS desktop 5rem(16px 루트에서 80px), Studio 계약 56px | 공식 웹 헤더와 Studio 상단 바를 별도 역할 토큰으로 분리 |
| 화면 간격 | 킷의 72~96px 수준 섹션 간격은 웹 페이지용 | 콘솔·Studio의 필드·툴바·표에 그대로 적용하지 않음. 업무 화면의 밀도는 별도 토큰으로 설정 |
| 강한 색 면적 | 스타일 문서의 10~20%는 기본 선호 | 할당량으로 강제하지 않음. 고객 사이트 고유 색을 제외한 레이어 크롬만 검토하고 필요한 만큼만 파랑 사용 |
| 폰트 | CSS는 Pretendard 우선 스택을 선언하지만 폰트 파일을 로드하지 않음 | 구현 시 실제 로딩, Figma 시 폰트 가용성 확인. 선언만으로 동일 폰트 렌더링을 보장하지 않음 |

새 문서는 시각 제작 기준을 보완한다. v5.7의 44페이지+19오버레이, 연결·과금·승인·복원·출시 게이트를 변경하는 지시로 해석하지 않는다. 브리프에는 사업기획서 27장을 제품·정책 기준으로 연결하고, 스타일과 제품 계약의 적용 영역을 구분하는 것이 적절하다.

## 4. 실제 토큰에서 확인한 주의점

### 보조 텍스트 대비

`--color-text-muted`는 `#747C88`이다. 로컬 계산 결과 흰색 배경 대비는 약 **4.22:1**, `#F7F8FA` 배경 대비는 약 **3.97:1**이다. 기존 LIVEPATCH 명세의 일반 텍스트 4.5:1 기준에 못 미친다. 이 색이 기본 적용되는 `.eyebrow`와 작은 안내 문구는 조정 대상으로 분류한다. 버튼 파랑 `#2764E7`과 흰색의 대비는 약 5.17:1이다.

현재 CSS 전체의 접근성 적합 판정을 내린 것은 아니다. 실제 배경·글자 크기·굵기·disabled 여부·포커스·상호작용은 화면별 검수가 필요하다.

### 공통 CSS와 고객 사이트의 분리

CSS에는 `html`, `body`, 제목·문단, `img/svg/video`, `box-sizing`에 대한 전역 규칙이 있다. 이를 편집 대상 사이트 문서에 그대로 주입하면 고객 사이트의 글꼴·여백·이미지·레이아웃이 바뀔 수 있다. LIVEPATCH 앱·편집 레이어의 스타일만 격리하고 고객 사이트에는 사용자가 승인한 패치만 적용해야 한다.

iframe·Shadow DOM 등 최종 격리 방식은 구현 구조에 맞춰 선택하되, 앱 토큰을 대상 페이지에 직접 적용하는 방식은 피한다. z-index 300/400 같은 내부 토큰만으로 외부 사이트의 모든 레이어보다 위에 표시된다고 보장할 수 없다.

### 기본 테마와 제품별 역할

기초 토큰은 재사용하고 Studio의 선택 경계·음성 상태·미리보기·검증·패스키·배포 결과 불명·복원 상태에 필요한 역할 토큰을 추가하는 편이 적절하다. CSS의 `Project theme`만 바꿔도 모든 제품 상태와 컴포넌트가 완성되는 구조는 아니다.

## 6. 다음 제작 전에 정리할 최소 항목

1. `design.md`에 서비스 정의·사용자·핵심 행동·출력 Figma 링크·v5.7 범위와 확정/가설 구분을 채운다. 구현 프레임워크는 기존 사이트의 지원 기술과 LIVEPATCH 앱 기술을 구분한다.
2. 콘셉트를 ‘고객 사이트를 주인공으로 두고, 번호와 음성으로 수정하는 한국어 작업 도구’ 방향으로 구체화한다. 아직 사용자 승인 콘셉트로 기록하지 않는다.
3. PC 메인 1920px 기준과 Studio 전체폭 예외, 공식 웹/콘솔의 콘텐츠 폭·정보 밀도를 기록한다.
4. 파랑 한 값·보조 텍스트 대비·공식 헤더/Studio 바·제품 상태 토큰을 정리한다.
5. Figma Foundations→Components→Studio 순서로 제작한다. 디자인킷이 추가됐다는 이유로 공식 랜딩을 핵심 Studio보다 앞서 제작할 필요는 없다.

검수는 `design.md` 16장의 평가표를 사용하되 미검증을 통과 처리하지 않는다. 핵심 행동 불능·원본 변형·승인 우회 같은 제품 오류는 시각 점수와 관계없이 차단한다. 현재는 아직 화면을 제작하지 않았으므로 디자인 점수나 사용자 승인을 부여하지 않는다.
